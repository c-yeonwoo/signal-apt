# Signal APT 2.0 제품과 시스템 설계

작성일: 2026-10-03. 검토 기준: main `9a582f0`. 상태: 구현 인계용 설계 완료, 미구현.

이 문서는 설명 가능한 시그널, 사용자 조건에 맞는 매물 발견, 독립 리포트를 중심으로 Signal APT를 확장하는 설계다. 대상 독자는 제품 책임자와 다음 구현 모델이다. 사용자가 승인한 방향은 **발견은 지도와 추천, 판단은 리포트와 비교, 추가 이해는 근거를 쉽게 풀어쓴 설명**으로 제공하는 것이다. 2026-10-04 제품 결정에 따라 Nick 채팅 진입점과 자유 입력은 제거했다. 기존 대화와 개인 자료는 이 UI 변경만으로 삭제하지 않는다.

이번 작업은 설계만 수행한다. 애플리케이션 수정, 모델 변경, DB 마이그레이션, 수집, 커밋, 머지, 배포는 포함하지 않는다. 실제 구현 순서와 검증은 [구현 인계](SIGNAL-APT-2.0-IMPLEMENTATION.md)를 따른다. 이 문서의 목표 수치와 신규 경로는 제안한 제품 계약이지 현재 구현이나 측정 결과가 아니다.

## 1 제품 목표와 범위

사용자가 관심 지역의 최근 변화를 이해하고, 자신의 조건에 맞는 후보를 찾고, 선택의 근거와 포기할 조건을 설명할 수 있게 한다. 거래 성사나 높은 매수 등급 자체를 성공 지표로 삼지 않는다. 보류하거나 후보를 제외하는 것도 유효한 결과다.

| 사용자 목적 | 첫 화면의 질문 | 완료 행동 |
| --- | --- | --- |
| 시장 공부 | 이번 주 무엇이 달라졌고 왜 중요한가 | 관심 지역과 판단 근거 저장 |
| 내 집 마련 | 내 조건에서 어떤 집을 비교해야 하나 | 2~3개 후보 비교 후 확인 항목 저장 |
| 투자 비교 | 기대하는 변화와 감당해야 할 위험은 무엇인가 | 가설과 반증 조건, 비용 가정 저장 |

목적은 사용자 선택이며 행동만으로 추정해 바꾸지 않는다. 목적 선택을 건너뛰면 시장 요약을 제공하고 자산·소득 입력 없이 탐색 가능하게 한다. 기존 사용자는 저장된 목적이 없으면 기존 구매 홈을 유지하고 전환을 안내한다. 개인용 원천의 접근권은 목적 선택과 무관하다.

첫 출시 범위는 시그널 설명, 조건 기반 발견, 지역·매물·비교 리포트, 맥락형 설명 버튼이다. 장기 예측 확률, 자동 투자 실행, 전면 지도 엔진 교체, 신규 원천 대량 크롤링, 경매 자동 권리판정은 포함하지 않는다. 시장 전망 모델과 경매 심화는 후속 단계다.

현재 확인된 선행 문제는 지역명 기반 키 충돌, 가격 결측·하락 중에도 긍정 두 조건으로 BUY가 가능한 규칙, 기본값 변경과 설정 버전의 불일치다. 운영 화면에서는 지도 타일 오류와 데이터 지연 안내가 관측됐다. 운영 문제의 원인은 아직 확정하지 않았으므로 배포·원천·브라우저 캐시를 각각 진단한다.

## 3 메뉴와 화면 흐름

목표 메뉴는 `이번 주 / 시장 지도 / 비교와 전략 / 내 기록`이다. 새 화면이 동작하기 전에 메뉴 이름만 먼저 교체하지 않는다. `내 조건`은 비교와 전략 및 계정 메뉴에서 항상 접근 가능하게 한다. 기존 hash 링크는 호환 라우팅한다.

| 화면 | 처음 보이는 정보 | 주요 행동 | 펼쳤을 때 보이는 정보 |
| --- | --- | --- | --- |
| 이번 주 | 중요 변화 최대 3개, 내 관심 변화, 목적별 후보 | 근거 보기, 관심 저장 | 전체 변화·수집 상태 |
| 시장 지도 | 같은 공간 수준의 지도·목록, 선택 레이어 하나 | 지역 선택, 지역 2~3곳 비교 | 추세·거래·전세·공급 상세 |
| 매물 발견 | 적용 조건, 후보 그룹, 추천 이유 | 후보 열기, 찜, 비교 담기 | 원천별 범위·확인 필요 후보 |
| 지역 리포트 | 등급, 판정 변화, 핵심 근거·반대 근거 | 이 지역 매물, 비교, 판단 기록 | 전체 지표와 발행 이력 |
| 매물 리포트 | 내 조건 적합성, 가격 성격, 장점·주의 | 비교, 저장, 확인 항목 | 입지·거래·건물·비용·원천 |
| 비교 리포트 | 동일 기준 2~3개 후보의 차이 | 조건 변경, 후보 교체 | 근거와 미비교 항목 |
| 내 기록 | 관심 지역·매물, 가설, 확인할 일 | 변화 확인, 복기 | 임장·과거 판단 |

### 3.1 리포트의 정보 순서

모든 리포트는 다음 순서를 공유한다.

1. 대상, 기준일, 상태와 한 줄 결론.
2. 판정 또는 추천을 설명하는 근거 최대 3개.
3. 반대 근거·양보할 점 최대 3개. 중대한 위험은 요약 제한과 무관하게 고정 노출.
4. 최근 달라진 점. 처음 관측한 경우에는 비교 불가라고 표시.
5. 미확인 사실과 판단이 바뀔 조건.
6. 다음 행동과 추가 설명 버튼.
7. 원천·기간·계산식·표본 상세.

지역 리포트는 시장 관측을, 매물 리포트는 해당 매물과 사용자 적합성을 다룬다. 지역 등급을 매물의 추천 등급으로 복사하지 않는다. 비교 리포트는 관측되지 않은 항목에 승자를 지정하지 않는다.

### 3.2 상호작용 계약

- 데스크톱은 목록·지도·상세 패널 구조다. 같은 카드 재클릭은 상세를 닫고, 다른 카드 클릭은 동일 패널 대상을 바꾼다. 찜·비교 버튼은 상세 토글을 유발하지 않는다.
- 리포트는 공유 가능한 앱 내부 경로를 가진다. URL에는 금융 조건·직장 좌표·사용자 질문을 넣지 않는다. 개인 리포트 링크는 링크 소지만으로 접근할 수 없다.
- 뒤로 가기는 리포트→직전 목록 상태로 돌아간다. 선택 지역·필터·지도 범위·스크롤을 세션 상태에 보존한다.
- 모바일은 목록과 지도 전환, 상세는 전체 화면으로 확장 가능한 하단 패널을 사용한다. 비교표는 항목별 카드로 전환해 가로 스크롤을 강요하지 않는다.
- 설명은 요약을 먼저, 상세는 펼침으로 제공한다. 반대 근거와 데이터 지연은 접힌 영역에만 숨기지 않는다.
- 본문 기본 16px, 조작 영역 최소 44px를 목표로 한다. 색상과 글자를 함께 사용하고 키보드·포커스·Escape·스크린리더 상태 안내를 지원한다.
- 요청 A 뒤에 B를 선택하면 늦게 도착한 A 결과를 폐기한다. 독립 섹션 실패는 다른 섹션을 지우지 않는다.

### 3.3 로딩과 빈 상태

상태는 `loading / ready / partial / stale / unavailable / forbidden`으로 나눈다. loading은 실제 미완료 요청에만 사용한다. 수집 결과 0건, 조건 부합 0건, 권한 없음, 원천 장애를 서로 다른 문장으로 표시한다.

LLM과 외부 경로 조회를 기다리지 않고 기본 리포트를 먼저 표시한다. 예전 리포트를 보여주면 당시 기준일과 현재 갱신 상태를 함께 표시하며 최신 결과처럼 꾸미지 않는다. 금액 0과 미확인은 구분하고, NaN·Infinity는 API에서 반환하지 않는다.

## 4 시그널과 설명 설계

### 4.1 등급의 의미

기존 내부 코드 `STRONG_BUY / BUY / WATCH / NEUTRAL / SELL_RISK`를 유지한다. 새 화면은 각각 `강력매수 / 매수 / 관망 / 중립 / 매도주의`로 표시하되 항상 `지역 시장 신호` 범위와 기준일을 붙인다. `SELL_RISK`는 개인에게 매도를 지시하는 뜻이 아니며, 과거 구간의 `SELL`과 동일하지 않다.

사용자에게 표시할 판정은 `raw_grade`, `display_grade`, `assessment_status`, `risk_flags`를 분리한다. 원래 규칙의 결과는 감사용으로 보존하고, 상태가 미확인·노후·충돌이면 주 배지는 `판단 보류`로 표시한다. 원래 결과를 보여줄 경우 상세에 `기존 규칙 산출값`으로 표시한다. 확률이나 적중률로 표현하지 않는다.

### 4.2 첫 버전의 안전 정책

새 가중치 최적화와 안전 정책을 분리한다. 초기 규칙의 숫자는 현재 값을 고정해 비교 기준선으로 남기고, 아래 정책은 별도 버전으로 관리한다.

| 조건 | 초기 표시 정책 |
| --- | --- |
| 동일 대상·주기의 최근 연속 4주 가격이 없거나 비유한 값 포함 | 판단 보류, 결측 항목 표시 |
| 핵심 심리·전세 지표 누락 또는 지역 매핑 충돌 | 판단 보류, 광역 추정으로 조용히 대체하지 않음 |
| 원천의 예상 공표일과 허용 지연을 초과 | 마지막 판정은 과거 기록으로만 제공, 현재 판정 보류 |
| raw BUY 또는 STRONG_BUY인데 4주 평균 가격 변화가 음수 | 판단 보류, 수급과 가격 방향 충돌 표시 |
| 보정 규칙이 SELL_RISK를 산출 | 매도주의와 해당 보정 근거 표시 |
| 보정에 필요한 보조 자료만 없음 | 기본 판정 가능하되 해당 위험은 미평가라고 고정 표시 |

양수·음수 방향과 현재 ±0.20% 추세 구간은 별도 필드다. −0.15%를 설명에서 `가격 변화 없음`으로 부르지 않는다. 음수 충돌 정책은 보수적인 UX 안전 규칙이며 예측력이 입증된 모델 변경이라고 주장하지 않는다. 중립·관망을 결측 상태의 대체값으로 사용하지 않는다.

신선도는 소스별 일정 manifest로 정한다. 주간 KB는 공식 일정 확보 시 예상 공표일 이후 48시간을 초기 유예로 사용한다. 일정이 미확인일 때는 최근 관측 기준일로부터 8일을 안전 상한으로 사용하고 일정 미검증을 표시한다. 2026-10-03 운영에서 12일 전 관측이 여전히 강력매수로 표시되는 불일치가 확인되어 기존 14일 상한을 보수적으로 낮췄다. 공휴일 등으로 주간 공표가 건너뛰면 보류가 늘 수 있으나 오래된 자료를 행동 신호로 제시하지 않는다. 매물은 검증된 수집시각 36시간 이내를 초기 fresh 기준, 그 이후 stale로 분리한다. 이 수치는 운영 기본안으로 설정 버전과 함께 저장하며, 정상 수집 주기가 다르면 원천별로 조정·테스트한다. 공표일 미확인을 수집시각으로 채우지 않는다.

### 4.3 판정 근거와 최근 변화

근거는 자유 문장이 아니라 다음 속성을 가진 결정적 레코드다.

| 필드 | 의미 |
| --- | --- |
| `reason_id`, `rule_id`, `evidence_ids` | 문장·규칙·원천 연결 |
| `role` | `driver / counterevidence / limitation / context` |
| `metric`, `value`, `unit`, `window` | 값과 해석 단위. 주간 평균과 누적을 구분 |
| `comparison` | 이전 값·비교 기간·차이·임계값·충족 여부 |
| `scope` | 관측 대상 지역과 적용 대상 지역, 직접·광역 상속 여부 |
| `effect` | 조건 충족·해제·위험 보정·표시 보류의 기여 |
| `template_key` | 검증된 설명 템플릿 |

지표가 높다는 사실만으로 실제 자금 유입·매매 전환·호재 효과의 발생을 단정하지 않는다. 예를 들어 전세수급 지표는 전세 압력의 근거이고, 매매 전환은 별도 관측이 없으면 가능성 설명이다.

이전 판정은 같은 지역 ID와 가장 최근의 이전 발행 기록에서 찾는다. 다음 변화 유형을 구분한다.

- `market_change`: 동일 규칙에서 관측값이 달라짐.
- `method_change`: 계산식·안전 정책·지역 매핑이 달라짐.
- `source_revision`: 같은 기준일 원천 수정으로 달라짐.
- `mixed_change`: 둘 이상이 함께 달라짐. 개별 기여를 증명할 수 없으면 단정하지 않음.
- `first_observation`: 비교 가능한 이전 발행 없음.

같은 규칙으로 이전·현재 자료를 재계산하면 조건 경계 통과를 설명할 수 있다. 그러나 이를 실제 과거 발행 결과로 저장하지 않는다. 최근 4주 근거 변화를 기본 노출하고 전체 이력으로 확장한다. 등급이 같아도 중요한 근거 변화가 있으면 설명한다.

### 4.4 판단 변경 조건

`rule_trigger`는 코드로 평가 가능한 실제 규칙 조건이다. 예를 들어 가격 기준 미달이나 자료 만료다. `watch_item`은 거래 회복·공급 확인처럼 아직 판정식에 포함되지 않은 관찰 항목이다. 둘을 혼용해 `이 조건이면 자동 등급 하락`이라고 말하지 않는다. 임의의 가격 목표나 LLM 생성 임계값을 사용하지 않는다.

### 4.5 미래 전망의 후속 검증

현재 등급은 동시점 관측 규칙이다. 미래 전망은 `target_metric / horizon / prediction / interval / model_version / issued_at`을 별도로 가진다. 먼저 단순 추세 기준선과 후보 모델을 비공개 병행 평가한다. 당시 사용 가능 자료, 신고 지연·원천 수정, 예측 기간의 중첩, 광역 지표 공유를 반영한다. 확률은 보정 성능이 검증됐을 때만 노출한다. 학습·검증 데이터 부족 또는 성숙 기간 미경과는 출시 일정으로 대체하지 않는다.

## 5 사용자 조건과 매물 추천

### 5.1 조건 계약

조건에는 `field / operator / value / unit / importance / origin / confirmed_at`을 저장한다. importance는 `must / prefer`, origin은 명시 입력·기존 프로필이며, 필수 여부를 모델이 임의 변경하지 않는다. 프로필은 독립 버전으로 관리한다.

- 필수 조건: 사용자가 지정한 가격 상한, 필요현금·월 부담 상한, 면적·방 수, 입주 시점, 통근시간 상한 등.
- 선호 조건: 연식, 브랜드, 역 접근성, 생활시설, 단지 규모 등. 같은 조건도 사용자가 필수로 승격할 수 있다.
- 자금 조건은 명시 가격 상한과 금융 계산 결과를 구분한다. 호가가 예산 안이라는 이유만으로 자금 조건 충족을 선언하지 않는다.
- 대출·세금·전세보증금·경매 비용은 기존 결정적 계산기를 재사용하고 검증 상태를 유지한다.
- 직장과 학교 등 개인 위치는 사용자가 명시한 조건만 사용한다. 민감한 개인 특성을 추론해 추천에 사용하지 않는다.

### 5.2 후보 선택 순서

1. 요청 사용자에게 허용된 원천과 지역 범위로 후보를 제한한다.
2. 원천 매물 ID로 중복 제거하고, 교차 원천 동일성은 확실한 경우만 병합한다. 명칭만 같은 후보는 동일 가능성만 표시한다.
3. 가격 성격·신선도·대상 식별을 검사한다. 경매 최저가와 청약 분양가는 일반 호가로 취급하지 않는다.
4. 필수 조건을 `pass / fail / unknown`으로 평가한다.
5. 모든 필수 조건 pass인 후보를 `조건 부합`, fail 없이 unknown이 있는 후보를 `확인 필요`, fail이 있는 후보를 `조건 초과`로 분리한다. 구매 승인이라는 표현은 쓰지 않는다.
6. 같은 그룹 안에서만 선호 적합도와 다양성을 적용한다. 시그널 등급으로 후보 풀을 제외하거나 자금 미확인을 부합으로 승격하지 않는다.

기본 추천은 조건 부합 그룹이며 확인 필요 그룹은 별도 섹션이다. 조건 초과는 자동 섞지 않고 사용자가 조건 완화 결과 보기를 선택할 때만 제공한다. 필수 조건이 아예 없으면 `탐색 후보`로 표시하고 개인 적합성을 주장하지 않는다. stale 후보는 마지막 관측 정보로만 보여주고 판매 가능 상태를 보장하지 않는다.

### 5.3 초기 순위 계산

첫 버전은 설명 가능한 결정적 정렬을 사용한다. LLM은 후보 선택이나 순위를 정하지 않는다.

각 선호의 충족도 `u_i`는 0~1, 중요도 `w_i`는 보통 1·중요 2·매우 중요 3이다. 수치형 상한·하한 조건은 사용자가 정한 목표에서 1이 되고 허용 범위 끝에서 0이 되도록 선형 계산한다. 범주형은 명시 선호 일치 여부로 계산한다. 허용 범위가 없으면 이진 충족만 사용한다. 높은 집값·유명 브랜드 자체를 보너스로 삼지 않는다.

`known_score = Σ(관측된 w_i × u_i) / Σ(전체 w_i)`

`coverage = Σ(관측된 w_i) / Σ(전체 w_i)`

알 수 없는 항목은 충족 점수를 주지 않으며 분모에서 빼지 않는다. 이는 미확인 후보가 유리해지는 것을 막기 위한 보수적 정렬 하한이며, 낮은 점수가 나쁜 집이라는 뜻은 아니다. score는 투자 수익률·확률·가격 적정성 점수가 아니다. 선호가 없으면 score를 만들지 않는다.

선형 값은 0~1로 clamp한다. 허용 범위가 역전되거나 폭이 0이면 입력 검증 오류로 처리하며 사용자 조건을 자동 수정하지 않는다. 상한·하한 중 어떤 방향이 선호인지 명시하고, 단위 변환 후 계산한다. 필수 조건 검사는 점수보다 먼저 적용한다.

그룹 내 기본 정렬은 known_score 내림차순, coverage 내림차순, 유효한 최신 수집시각 내림차순, stable listing ID 순이다. 특정 카드 그룹은 목적에 맞는 값으로 먼저 정렬할 수 있지만 해당 수치가 검증된 후보만 포함한다. 시그널은 카드의 맥락 정보이며 초기 기본 순위의 가중치로 쓰지 않는다.

첫 12개에서 같은 단지 최대 2개를 먼저 배치하고 초과 후보를 뒤로 보낸다. 광역 탐색에만 동일 시군구 최대 4개를 같은 방식으로 적용한다. 특정 지역·단지를 명시 선택했으면 해당 다양성 제한을 끈다. 후보를 삭제하지 않으며 hard 그룹 경계를 넘지 않는다. 초기 UX 설정값이지 최적 수익 가중치가 아니다.

### 5.4 추천 카드 그룹

| 그룹 | 구성 근거 | 정보 부족 시 |
| --- | --- | --- |
| 조건에 잘 맞는 집 | 필수 조건과 선호 적합도 | 확인 필요 후보를 분리 |
| 월 부담이 낮은 대안 | 동일 금융 가정의 총월부담 | 호가만으로 대체하지 않음 |
| 통근이 편한 대안 | 동일 목적지·이동수단·기준의 경로 | 직선거리로 통근시간을 꾸미지 않음 |
| 더 넓은 대안 | 같은 예산 범위 내 전용면적 | 면적 미확인 제외 |
| 관심 단지의 새 매물 | 확정 단지 ID와 최초 관측 | 실제 신규 등록과 구분 |

처음에는 근거가 있는 그룹 최대 3개만 노출한다. 한 카드의 기본 문장은 `추천 이유 / 양보할 점 / 확인할 점`이다. 공급자 표시인 급매·찐매물은 검증된 저평가 판정과 분리한다. 카드 설명은 실제 정렬에서 사용한 reason ID를 참조해야 한다.

후보가 없으면 어느 조건 때문에 몇 건이 제외됐는지 권한 범위 안에서 집계한다. `면적을 줄이면`, `인접 지역을 포함하면`처럼 한 조건씩 완화한 결과를 제안하되 사용자가 적용하기 전 저장 조건이나 기본 결과를 바꾸지 않는다. 필수 예산 상한도 예외가 아니다.

## 6 공통 데이터 계약

다음 이름은 신규 구현의 계약 초안이다. 기존 API를 즉시 교체하지 않고 버전 어댑터로 연결한다. 금액은 만원, 면적은 전용 제곱미터, 시간은 분, 시각은 timezone을 포함한 ISO 8601로 통일한다. 날짜만 아는 원천 값은 date로 보존하고 자정 시각을 만들어 넣지 않는다.

### 6.1 핵심 개체

| 개체 | 필수 내용 |
| --- | --- |
| `EntityRef` | entity_type, canonical_id, display_name, parent_id, spatial_grain, identity_status, 원천 ID 매핑 |
| `Evidence` | evidence_id, entity, metric, value 또는 null, unit, 관측 기간, observed_at, published_at, fetched_at, available_at, source_id, source_revision, sample_n, 상태, 직접·상속 범위 |
| `SignalAssessment` | assessment_id, schema_version, entity, issued_at, input_revision_ids, config_hash, guard_version, raw_grade, display_grade, assessment_status, reasons, risk_flags, previous_assessment_id, change_type |
| `NeedProfile` | profile_id, uid, version, 목적, 필수·선호 조건, 입력 출처와 확인일 |
| `RecommendationItem` | listing_ref, eligibility, constraint_results, preference_results, rank_key, rank_version, 이유·양보·미확인, report_ref |
| `Report` | report_id, schema_version, report_type, subject_refs, access_scope, profile_hash, evidence_hash, assessment_refs, section 상태, facts, reasons, next_actions, freshness, narrative_ref |
| `Narrative` | narrative_id, report_id, action, evidence_hash, model_version, prompt_version, 생성시각, 검증 상태, 구조화된 설명 |
| `DecisionNote` | note_id, uid, subject_refs, report_id, 가설, 기대 기간, 반증 조건, 확인할 일, revision, 작성·수정시각 |

`available_at`은 우리 시스템이 실제로 확보해 판단에 사용할 수 있었던 시각이다. published_at을 모르면 null이며, 과거 날짜의 자료를 오늘 수집했다고 당시 사용 가능했던 자료로 인정하지 않는다. 데이터 원천 URL은 허용 프로토콜과 도메인 정책을 검증한다.

리포트 본문에 근거 없는 값과 참고 링크만 붙이는 방식은 금지한다. 각 수치·판정·추천 이유가 evidence ID 또는 결정적 계산 ID에 연결돼야 한다. 수집 건수와 시장 전체 건수를 구분한다. 단지 위치와 검증된 출입구·통학 배정은 별도 속성이다.

### 6.2 지역과 단지 식별

행정구역 ID와 KB 같은 통계 권역 ID는 별도 namespace로 관리한다. `강북14개구` 같은 통계 집계를 법정동코드로 위조하지 않는다. 명칭은 표시용이며 join key가 아니다. 지역 매핑에는 source_id, source_region_id, canonical_id, parent, valid_from, valid_to를 둔다.

단지는 원천 단지 ID·주소·좌표를 통해 canonical ID에 연결한다. 출처가 다른 ID를 그대로 같은 단지로 간주하지 않는다. 중구처럼 기존 자료가 이미 이름으로 덮어써진 경우 코드만 고쳐 데이터를 복원했다고 주장하지 않는다. 복원 가능한 원천 자료만 재구축하고 불가능한 과거는 ambiguous로 남긴다. 지역·단지 동명이인 회귀 테스트가 완료되기 전 해당 자료를 추천·검증 표본에 넣지 않는다.

### 6.3 저장과 발행

SQLite 영속 볼륨과 기존 immutable 원천 저장을 유지한다. 신규 테이블은 additive migration으로 추가한다. 역할은 다음과 같다.

- `entity_mappings`: 원천 ID와 canonical ID의 유효기간 매핑.
- `signal_assessments`: 발행 판정과 입력·설정 참조. 같은 입력 재시도는 같은 ID로 중복 방지.
- `report_snapshots`: 버전이 고정된 구조화 리포트. 최신 포인터와 과거 내용 분리.
- `report_narratives`: 리포트 근거 해시에 연결된 설명 캐시와 작업 상태.
- `need_profiles`: 기존 프로필과 호환되는 명시 조건 버전.
- `decision_notes`, `decision_note_revisions`: 사용자 판단과 수정 이력.

실제 발행과 연구 재계산은 `record_kind=issued / reconstructed`로 구분한다. 기존 이력은 발행 사실을 증명할 수 있을 때만 issued로 이관한다. 사용자 note·프로필·개인 리포트는 삭제·탈퇴 정책의 대상이며, 불변 시장 기록이라는 이유로 영구 보관하지 않는다.

현재 snapshot·KV 소비자는 새 저장의 호환 read model을 읽도록 전환한다. 발행 처리에서 DB 트랜잭션으로 판정·최신 포인터·알림 outbox를 기록하고, 기존 JSON 캐시 갱신은 outbox 재시도로 처리한다. 파일 쓰기 실패 때문에 판정이 두 번 발행되거나 알림이 중복되지 않게 한다. 중복 키는 대상·입력 해시·규칙·표시 정책 버전으로 구성한다.

### 6.4 리포트 갱신과 버전 일관성

리포트에는 같은 대상·접근 scope·개인 조건 조합을 가리키는 `report_family_id`와 내용을 고정하는 `report_id`를 둔다. report_id는 정규화된 근거 revision, 규칙·안전·자금 정책 버전, profile hash, access scope, schema version으로 결정한다. 생성시각·캐시 hit 같은 일시적 값은 내용 해시에서 제외한다. 사용자별 해시는 사용자 scope를 포함하며 공개 API에 전체 캐시 키를 노출하지 않는다.

기본 자료만 있는 리포트 R1에 입지·건물 자료가 추가되면 R1을 덮어쓰지 않고 `supersedes_report_id=R1`인 R2를 만든다. R1용 설명은 R2용으로 재사용하지 않는다. 오래 열린 화면은 `새 자료가 도착했습니다`를 표시하고 명시 갱신 또는 동일 선택 상태의 안전한 교체로 R2를 적용한다. 읽고 있던 펼침·스크롤은 유지한다. 과거 기록 화면은 R1 그대로 남는다.

발행 당시 fresh였던 판정은 시간이 지나도 저장 내용이 바뀌지 않는다. 최신 화면은 별도의 `serving_freshness`를 계산해 오래된 판정을 현재 추천으로 보이지 않게 한다. 이는 발행 이력 수정이 아니라 현재 사용 적합성 표시다. cache hit마다 권한·신선도를 재검사하고, 리포트 저장 내용과 현재 경고를 구분한다.

동일 근거·조건·버전에서 출력이 달라지면 결정성 오류로 취급한다. 새로운 보강 job은 근거 revision을 반환하고 리포트 빌더가 새 판을 생성한다. job 결과가 도착했다는 이유만으로 브라우저에서 다른 버전의 숫자를 기존 리포트에 덧붙이지 않는다.

## 7 API와 비동기 처리

모든 `/api/v2` 경로는 제안이며 아직 존재하지 않는다. Pydantic 계약을 먼저 확정하고 기존 JSON 응답 관례와 오류 핸들러를 재사용한다. 서버가 session에서 uid와 원천 권한을 결정한다. 클라이언트가 보낸 가격·등급·uid는 판단 입력 정본으로 신뢰하지 않는다.

| 신규 경로 | 역할 |
| --- | --- |
| `GET /api/v2/regions/{region_id}/report` | 최신 지역 리포트와 판정 변화 |
| `GET /api/v2/listings/report?key=...` | 현재 권한으로 조회한 매물 기본 리포트 |
| `POST /api/v2/comparisons` | 서로 다른 2~3개 key로 비교 리포트 생성 또는 재사용 |
| `POST /api/v2/discovery` | 목적·조건·지역·페이지 커서로 추천. 조건은 URL에 넣지 않음 |
| `GET /api/v2/reports/{report_id}` | 권한 재검사 후 고정 리포트 조회 |
| `POST /api/v2/reports/{report_id}/explanations` | easy, counterevidence, compare, question 중 요청 |
| `GET /api/v2/report-jobs/{job_id}` | 사용자 또는 공유 범위 권한을 검사한 생성 상태 |
| `GET /api/v2/need-profile`, `PUT /api/v2/need-profile` | 명시 조건 조회·버전 검사 저장 |
| `GET /api/v2/decision-notes`, `POST /api/v2/decision-notes` | 개인 가설 조회·생성 |
| `PATCH /api/v2/decision-notes/{id}`, `DELETE /api/v2/decision-notes/{id}` | revision 충돌 검사 수정·삭제 |

GET은 유료 LLM 호출과 원천 refresh를 시작하지 않는다. 이미 수집된 자료로 결정적 read model을 구성하거나 기존 job 상태를 반환할 수 있다. 외부 경로·입지 보강이 필요한 경우 `POST /api/v2/reports/{report_id}/enrichments`로 필요한 섹션만 요청한다. 자동 기본 보강은 수집 worker가 담당하며 개인 목적지 조회는 사용자가 요청한 경우에만 수행한다.

새 설명·보강 작업은 캐시 hit이면 200, 큐에 수락되면 202와 job ID를 반환한다. 입력 오류 422, 로그인 필요 401, 권한 없음 403, 찾을 수 없는 대상 404, 버전 충돌 409, 비용·속도 제한 429를 구분한다. 리포트 일부 원천 장애는 section unavailable이며 전체 500으로 처리하지 않는다. 원천 권한을 유추시키는 조회는 기존 정책에 맞춰 404로 통일할 수 있다.

작업 상태는 queued, running, succeeded, failed, cancelled다. 서버 deadline·최대 시도·lease 만료 복구를 둔다. 같은 사용자·동일 리포트·동일 요청은 idempotency key와 evidence hash로 합친다. 화면은 작업 중 이탈해도 기본 리포트를 유지하고, 결과 완료 후 보고 있는 report ID와 일치할 때만 붙인다. polling은 2초→5초→10초로 backoff하며 숨김 화면에서는 중단한다. 세션 만료·권한 회수 시 결과를 보여주지 않는다.

발견 페이지는 20개씩, 최대 50개 요청을 허용하고 후보 스냅샷과 조건 해시를 cursor에 묶는다. 정렬 중 데이터가 바뀌면 snapshot_changed를 알려 새로 시작한다. 원천 권한은 각 페이지에서 재검사한다. 보강은 선택 후보 또는 비교 후보 최대 3개로 제한하고, 모든 후보의 경로·LLM 분석을 요청 중에 수행하지 않는다.

## 8 AI 설명과 Nick 전환

### 8.1 설명 생성 원칙

핵심 판정 문장과 추천 이유는 결정적 템플릿으로 항상 제공한다. LLM은 동일한 근거 묶음에서 쉬운 해석·반대 관점·질문 응답을 제공한다. 보고서를 잘 만들기 위해 LLM이 필수인 구조로 만들지 않는다.

입력은 사용자 권한을 거친 Report, 허용된 Evidence, 명시 질문이다. 외부 기사·매물 설명은 비신뢰 자료로 취급하고 도구 실행 지시나 시스템 명령으로 사용하지 않는다. 프로필·직장 좌표·사용자 질문을 공유 분석 캐시에 넣지 않는다. 원천별 개인 전용 자료는 비개인적 내용처럼 보여도 공개 캐시에 넣지 않는다.

출력은 section과 claim별 evidence ID를 포함한 구조화 형식으로 제한한다. 등급·금액·기간·좌표·확률·학교 배정·법적 자격은 LLM 출력에서 채택하지 않는다. 수치 슬롯은 서버에서 근거값으로 렌더한다. 자유 설명에 새로운 수치·단정·참조 없는 근거가 섞이면 검증 실패로 처리하고 해당 부분을 결정적 설명으로 대체한다. 이 검증이 모든 의미 오류를 증명상 제거한다고 주장하지 않으며 반례 테스트와 사람 검수를 병행한다.

통계적 상관을 원인으로 단정하거나 긍정 요소만으로 결론을 정당화하지 않는다. 같은 리포트의 사실·한계·반대 근거를 모든 표면에서 공유한다. evidence hash가 바뀌면 기존 설명을 최신 리포트에 붙이지 않는다. LLM timeout·예산 초과·검증 실패에도 기본 판정과 비교 기능은 정상 동작해야 한다.

### 8.2 채팅 UI 제거 후 리포트 중심 동선

1. 리포트 DOM·상태·라우팅을 advisor 패널 밖으로 분리하고 자동 모델 호출을 없앤다.
2. 매물 가격·예산·주의 근거는 정형 요약 버튼으로 즉시 다시 보여 준다. `쉽게 설명 / 반대 근거`는 선택형 근거 제한 설명으로 유지하되 자유 입력형 채팅은 제공하지 않는다.
3. 전역 Nick 버튼과 지역·매물·비교의 질문 진입점을 제거한다. 구형 리포트 롤백 패널은 채팅 없는 읽기 전용 화면으로 유지한다.
4. 기존 대화·메모리는 삭제하지 않는다. 구형 `/api/advisor` 채팅 요청은 `410`으로 종료해 모델 호출·사용량 차감을 막고, 메모리 조회·삭제 API는 남긴다. 개인 자료의 최종 보존·폐기는 별도 정책으로 결정한다.

사용자 조건 변경은 명시 저장 동작이 있어야 반영한다. 예전 대화에서 추출한 선호를 신규 필수 조건으로 자동 승격하지 않는다.

## 9 캐시와 비용

공통 시장 사실, 원천 접근 제한 사실, 개인 적합성을 분리한다. 기존 공통 비용 게이트·원가 기록·동시성 제한을 재사용하며 애플리케이션 모델 등급을 임의로 낮추지 않는다. 다음 구현 모델을 sol로 바꾸는 것과 서비스 내 LLM 설정은 별개다.

| 캐시 계층 | 키의 핵심 | 무효화 |
| --- | --- | --- |
| 공개 시장 사실 | canonical ID, 원천 revision, 계산·schema 버전 | 원천 수정·계산 변경 |
| 접근 제한 매물 사실 | 권한 scope, 원천 ID, revision | 권한·호가·상태·원천 변경 |
| 개인 추천·리포트 | uid, 권한 version, profile hash, evidence hash, ranking·policy 버전 | 조건·권한·금융 가정 변경 |
| AI 설명 | 위 scope, report hash, action, model·prompt 버전 | 근거·요청·모델·프롬프트 변경 |

캐시 TTL은 데이터 신선도 판정을 대체하지 않는다. 새로 캐시했다고 오래된 원천이 fresh가 되지 않는다. logout 시 브라우저 개인 캐시·진행 중 요청을 비우고 다른 계정에 재사용하지 않는다. 개인 응답에는 private/no-store 정책을 적용하고 공유 CDN에 저장하지 않는다.

기본 탐색·지도 조작·찜·비교는 LLM 0회다. 공개 주간 설명의 사전 생성은 관심이 있는 지역의 변경된 근거에 한정한다. 그 외 심화 생성은 요청 시 실행한다. 모든 비용은 uid 또는 shared scope, 기능, report ID, model·prompt 버전별로 기록한다. 실제 공급자 가격과 청구서는 구현·운영 시 다시 확인하며 이 설계에 월 비용 보장값을 두지 않는다.

성능 초기 목표는 서버 warm cache 기준 발견 p95 500ms 이하, 기본 리포트 p95 800ms 이하, 합의한 모바일 시험 조건에서 주요 내용 2초 이내다. cold·외부 보강·LLM 시간은 별도 계측한다. 목표를 달성했다고 사전 주장하지 않는다. SQLite 단일 영속 볼륨을 유지하고 worker를 분리하더라도 같은 저장과 lease를 사용한다. 복제본 증설은 별도 저장 설계 없이는 하지 않는다.

## 10 알림과 판단 기록

찜은 기존 기능을 재사용한다. 가설 저장은 선택 입력으로 추가하며 저장하지 않아도 탐색을 막지 않는다. DecisionNote에는 관심 이유·예상 기간·반증 조건·다음 확인·기준 report ID를 둔다. 수정은 새로운 revision이며 과거 생각을 현재 문장으로 덮어쓴 복기 결과를 만들지 않는다.

알림은 등급 변화뿐 아니라 중요한 근거의 변화, 관심 매물 호가 변화, 새 대안, 사용자가 정한 관찰 조건을 지원한다. 시스템 규칙 평가와 사용자가 작성한 문장형 가설은 구분한다. 자유 문장 가설을 LLM이 임의로 충족 판정해 매수·매도 알림을 보내지 않는다.

이벤트 중복 키는 uid·대상·이벤트 종류·근거 revision이다. 같은 변화는 묶고 채널 실패와 시장 변화 없음을 구분한다. 발송 채널은 현재 권한·설정으로만 사용하며 자동 구독이나 테스트 발송은 하지 않는다. 실제 전망 결과와 단순 가격 변화를 구분해 4·12·26주 복기에 표시한다.

## 11 검증과 출시 조건

| 검증 영역 | 반드시 확인할 내용 |
| --- | --- |
| 판정 | 결측·오래된 자료·하락 충돌, 경계값·단위, 광역 상속, 숫자 설명과 규칙 일치 |
| 발행 이력 | 설정 변경으로 과거 발행이 바뀌지 않음, 재시도 중복 방지, 원천 수정 분리 |
| 추천 | 모든 필수 조건 검사, unknown 분리, 개인 권한, 중복 제거, 결정적 정렬·pagination |
| 리포트 | 모든 핵심 주장에 유효한 근거, 반대 근거 보존, 비교 단위·기간·가격 성격 일치 |
| AI | 미제공 숫자·인과·권리 확정 거부, prompt injection, 비용 초과·실패 fallback |
| UI | 재클릭 접힘, 뒤로가기, 계정 전환, A→B 지연 응답, 키보드, 모바일, 부분 실패 |
| 운영 | 원천·캐시 기준일, source health, job 재시도, rollback, 백업 복원 |

초기 사용자 과업 목표는 초보 사용자 5명 중 4명이 3분 안에 특정 지역의 판정 이유와 반대 근거를 찾고, 추천 두 후보의 차이를 설명하는 것이다. 작은 표본의 탐색적 UX 검사이며 통계적 효과 입증이 아니다. 예측 성능 검증을 대신하지 않는다.

출시 지표는 근거 펼침, 비교 완료, 조건 수정 후 후보 재발견, 판단 기록과 복기다. 사건 로그에는 원문 질문·재산·소득·정확한 위치를 넣지 않는다. 클릭 수 증가만으로 품질 개선을 판정하지 않는다.

## 12 확정 결정과 남은 검증

확정 설계는 독립 리포트 우선, 시그널 등급 유지와 의미·안전 상태 구분, 필수 조건 우선 추천, 판정 근거의 단일 데이터 계약, Nick 단계적 비중 축소, 기존 개인 원천 권한 유지다.

구현 중 검증할 항목은 지도 공급자 정상 설정, 운영 수집 지연 원인, 지역 원천 수정·복원 범위, 소스별 공표 일정, 실제 경로 API 제약, 성능·비용 실측이다. 미검증 상태에서는 관련 값을 unknown으로 유지하고 해당 기능만 제한한다. 전체 출시를 핑계로 추정값을 사실로 채우지 않는다.

후속 의사결정이 필요한 항목은 새 전망 모델의 운영 승격, 독립 Nick API와 과거 대화의 최종 폐기, 외부 원천 추가 계약·공개 범위 변경이다. 기본 구현은 이 결정을 기다리지 않고 설명·발견·비교 개선을 진행할 수 있다.
