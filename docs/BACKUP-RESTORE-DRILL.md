# 운영 DB 백업 복원 점검

현재 서비스는 SQLite `app.db`를 온라인 스냅샷으로 만들고 `signalapt/app-YYYYMMDD-HHMMSS.db.gz` 형식으로 S3 호환 저장소에 업로드한다. 업로드 성공이나 `/ready` 200만으로 복원 가능성이 입증되지는 않는다.

새 백업 작업은 업로드 직후 원격 객체를 다시 읽어 임시 DB에 복원하고, SQLite 무결성·필수 테이블·업로드한 바이트의 SHA-256 일치를 확인한 뒤에만 성공으로 기록하고 이전 객체 보관 정리를 시작한다. 이 자동 검증이 실패하면 옛 백업을 정리하지 않는다. 다만 새 객체 하나의 즉시 읽기 검사는 보관 기간이 지난 객체나 볼륨 장애 복구를 증명하지 않으므로 아래 운영 점검은 여전히 필요하다.

관리자 `/api/operations`의 `backup.configured`와 `backup.upload_job`을 먼저 확인한다. 설정이 없거나 업로드가 실패하면 스케줄러는 성공 시각을 새로 기록하지 않고 각각 `BackupNotConfigured`, `BackupUploadFailed` 오류 유형을 남긴다. 이전 `last_success`는 과거 업로드 이력일 수 있으므로 현재 설정과 마지막 시도 결과를 함께 읽어야 한다. `/ready`의 `kb_source_fresh_for_signal`은 KB 관측일의 8일 제한만 나타내며, 지역별 판정 준비 여부나 백업 복구 가능성을 뜻하지 않는다.

## 읽기 전용 복원 점검

1. Railway 작업 로그 또는 저장소에서 최근 성공한 백업의 정확한 오브젝트 키를 확인한다. 키에 계정 비밀값을 넣지 않는다.
2. 백업 S3 환경변수가 설정된 격리 실행 환경에서 `signal backup-verify signalapt/app-YYYYMMDD-HHMMSS.db.gz`를 실행한다. 이 명령은 원격 객체를 읽고 임시 파일에만 복원한다. 서비스 `app.db`를 교체하거나 S3 객체를 삭제하지 않는다.
3. 종료 코드 0, `integrity=ok`, 복원 바이트 수, `users/profile/favorites/kv` 행 수와 SHA-256을 점검 기록에 남긴다. 행 수는 기대치와 비교하되 사용자 데이터 내용이나 자격증명은 출력하지 않는다.
4. 최근 백업뿐 아니라 보관 기간 안의 과거 백업 하나도 확인한다. 실패 시 업로드 성공을 복구 성공으로 보고하지 말고 원본 백업을 보존한 채 원인을 조사한다.

이 명령은 임시 복원·무결성 점검까지만 증명한다. Railway 볼륨의 실제 교체, 서비스 재기동, 최신 JSON/parquet 원천과의 정합성, 복구 시간 목표는 별도의 승인된 운영 리허설이 필요하다. 검증 전에는 2.0 출시의 백업·복구 게이트를 완료로 표시하지 않는다.
